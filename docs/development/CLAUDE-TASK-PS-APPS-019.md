## 2. Подтверждённое состояние — API готов, клиентская интеграция у Claude

В WEB уже реализованы:

- Выборочное удаление записей: `POST /api/consoles/tasks`, `action:"remove"`, с `consoleId`, точным `queueId` и **одним** из `packageIds` / `branches`.
- Остановка выбранной переустановки PS4: тот же маршрут, `action:"stop-reinstall"`, `queueId` здесь является ID процесса переустановки.
- `canDismiss` у строк общего списка задач; `canCancel` с поддержкой пользовательской переустановки и неотправленного хвоста ошибочной очереди.

**Codex подключил и проверил новые команды в `/api/catalog/v1/command` и `/api/catalog/v2/command`.** Оба activity публикуют `taskControls`, стабильный `packageId`, `branchId`, права и телеметрию; PS4 передаёт `maintenance`. Контракт разделов 4–5 теперь реализован. Проверены production helper-тесты, настоящие HTTP-маршруты собранного Nuxt и сборка WEB. Ответы приставок в HTTP-тесте синтетические; проверки на PS4/PS5 этим не подтверждаются.

## 3. Сохранить работающий интерфейс и соединение

Сохранить подтверждённое пользователем в кандидате PS5 WEB 040: родную IME по △, ввод/отмену/повторное открытие, левый стик и удержание крестовины через границы страниц, счётчики патчей/DLC, панель сведений/R3, фильтры/сортировку L2, избранное, пресеты, скорость и этапы установки. Не брать старый eboot от тестовых контейнеров в качестве основы новой сборки.

PS4 использует существующие настройки WEB и идентичность своей приставки. PS5 получает сопряжённый WEB через существующий loopback-путь службы `127.0.0.1:8095/api/v1/ui/status`; адрес WEB, порт и `consoleId` должны совпадать с сопряжённым назначением. Bearer-ключ остаётся в WEB/ELF: приложение его не получает и не хранит.

Новые команды отправлять тем же HTTP-клиентом и тем же worker, что существующие команды. `Content-Type: application/json`; `Origin` не добавлять для нативного клиента, либо он должен точно совпадать с origin WEB. Не добавлять localhost в качестве адреса WEB на приставке. Не менять таймауты, разрешённые адреса, редиректы и авторизацию ради прохождения теста.

При смене профиля/адреса WEB увеличить существующую ревизию конфигурации, сбросить выбор и не применять ответ старого профиля. При потере соединения показать последние данные как устаревшие и выключить изменяющие действия до свежего подтверждённого ответа. Запросы выполнять вне потока отрисовки.

## 4. Контракт чтения заданий (реализован Codex)

PS4:

```text
GET /api/catalog/v1/activity?ip=<PS4_IP>&source=tasks&page=1&mask=15&lang=ru
```

PS5:

```text
GET /api/catalog/v2/activity?consoleId=<PROFILE_ID>&source=tasks&page=1&mask=15&lang=ru
```

Сохранить `tasks`, `queueId`, `queueStatus`, `currentPackageId`, `taskPage`, `taskPages`, `taskTotal`, `counts`, `message`. У v2 сохранить `schemaVersion:2`, `consoleId`, `consolePlatform:"ps5"`. Маска: active=1, queued=2, completed=4, failed=8. Активные задания закреплены вне фильтра истории; убрать дубликаты по ключу строки.

Реализованы поля **без изменения смысла прежних**:

```json
{
  "taskControls": {
    "version": 1,
    "actions": ["remove-items", "remove-games", "stop-reinstall"]
  },
  "maintenance": {
    "id": "<FLOW_ID>",
    "title": "Выбранные пакеты",
    "state": "<FLOW_STATE>",
    "message": "<REAL_MESSAGE>",
    "canStop": true
  }
}
```

`taskControls` публикуется только после подключения и проверки соответствующих обработчиков. У PS5 `stop-reinstall` в actions отсутствует. `maintenance` необязателен и для этого задания относится только к PS4 `selected-reinstall`; это не разрешение остановить обновление службы или любой служебный процесс.

Каждая строка получает `packageId`, `branchId`, `canDismiss`, `canCancel`, `cancelRequested`, `category`, а также доступные `bytesSent`, `size`, `progressPhase`, `bytesChecked`, `transferBytesPerSecond`, `transferMeasuredAt` без подмены отсутствующих значений фиктивным успехом.

Особенности идентификаторов:

- PS4 существующий `tasks[].id` в v1 равен package ID. Не менять его для старого клиента. Новое `packageId` дублирует этот стабильный ID явно.
- PS5 `tasks[].id` — ID попытки передачи; **он не является package ID**. Для новых `remove-items` передавать именно `tasks[].packageId`. Старые cancel-команды и их разрешение opaque ID сохранить совместимыми.
- `branchId` создаёт WEB по тем же правилам, что helper удаления: PS4 `ps4:<titleId>` или `ps4:<packageId>` при отсутствии titleId; PS5 — точный `item.branch`, например `ps5:PPSA01325`. Не вычислять его из отображаемого названия.
- Для удаления берётся `tasks[].queueId`, включая историческую очередь, а не общий текущий `queueId` страницы.
- Выбор хранить по `(назначение, queueId, packageId)`; индекс строки, название и совпадение обложки не являются ключом команды.

Булевы значения парсить строго: отсутствующее поле, строка `"true"`, null и неизвестная версия возможностей не включают новую кнопку. В старом WEB оставить доступные старые cancel/clear действия; новые remove/stop не отправлять.

## 5. Контракт команд (реализован Codex)

Маршруты не меняются:

| | Отправка | Квитанция |
|---|---|---|
| PS4 | `POST /api/catalog/v1/command` | `GET /api/catalog/v1/command?ip=<PS4_IP>&id=<REQUEST_ID>` |
| PS5 | `POST /api/catalog/v2/command` | `GET /api/catalog/v2/command?consoleId=<PROFILE_ID>&id=<REQUEST_ID>` |

Добавить действия `remove-items`, `remove-games`; только PS4 — `stop-reinstall`. Существующие enum действий 1–15 в клиентах не перенумеровывать. Новые значения, включая `install-reviewed`, добавлять в конец, но условия типа `command_action>=14` заменить явной классификацией: новая stop-команда не должна случайно стать пакетной или cancel-командой.

Пример выбора записей PS4:

```json
{
  "ip": "<PS4_IP>",
  "requestId": "0123456789abcdef0123456789abcdef",
  "gameId": "tasks",
  "action": "remove-items",
  "queueId": "<EXACT_QUEUE_ID>",
  "packageIds": ["<PACKAGE_ID_1>", "<PACKAGE_ID_2>"]
}
```

Пример ветки PS5:

```json
{
  "consoleId": "<PROFILE_ID>",
  "requestId": "fedcba9876543210fedcba9876543210",
  "gameId": "tasks",
  "action": "remove-games",
  "queueId": "<EXACT_QUEUE_ID>",
  "gameIds": ["ps5:PPSA01325"]
}
```

Для PS4 `remove-games` структура аналогична с `ip` вместо `consoleId`, а `gameIds` содержит **новые branchId**, например `ps4:CUSA07027`. Старый `cancel-games` продолжает использовать свой существующий контракт; не менять его автоматически на новый формат. В валидаторе PS4 разрешить двоеточие только там, где нужен branchId, а не отключать проверку всех ID.

Пример остановки PS4:

```json
{
  "ip": "<PS4_IP>",
  "requestId": "00112233445566778899aabbccddeeff",
  "gameId": "tasks",
  "action": "stop-reinstall",
  "maintenanceId": "<FLOW_ID_FROM_ACTIVITY>"
}
```

`maintenanceId` намеренно отдельный: клиент не подставляет текущий queueId вместо ID процесса. WEB вызывает `stopSelectedReinstall(ip, maintenanceId)`. Для этой команды **не сериализовать** queueId, packageIds или gameIds, даже пустые: они отклоняются. Для remove-items не сериализовать gameIds, для remove-games — packageIds; maintenanceId у обоих отсутствует.

На сервере уже реализовано Codex:

1. Добавляет строгую валидацию новых действий и массивов (непустые, не более 256 ID для нативной команды, без обрезания), точного queueId/maintenanceId и назначения.
2. Включает action, назначение, queueId, выбранные packageIds/gameIds и maintenanceId в fingerprint. Список можно нормализовать/дедуплицировать до fingerprint; переставленные одинаковые ID не меняют выбор.
3. Сохраняет квитанцию до побочного действия.
4. PS4 remove вызывает `removeInstallationTasks(ip, queueId, packageIds, branches)`; PS5 — `removePs5Tasks(consoleId, queueId, packageIds, branches)`. Не ограничивать эти новые действия только текущей running-очередью: завершённая историческая попытка тоже удаляема.
5. Использует существующие helper-проверки живых заданий и защищённых служебных очередей. Не удаляет receipts, элементы массива runner и исходные файлы; не меняет installed-метки ради очистки UI.
6. Возвращает реальное сообщение helper через существующую квитанцию. Старые requestId с тем же телом читают результат; другое тело с тем же ID отклоняется.
7. Исправляет проверку старого `cancel-all` для разрешённого неотправленного хвоста failed-очереди PS4, сохраняя защиту обновления службы.

PS4 квитанция: `pending → accepted|failed|uncertain`. PS5: `pending → completed|failed|uncertain`. Это результат **команды**, не факт установки игры и не обязательное завершение удалённой отмены. HTTP 200 с `state:"failed"` — ошибка действия, а не успех. После терминального ответа перечитать activity.

### 7.1. Обнаружение возможностей и preview

Каталог `GET /api/catalog/v1` или `GET /api/catalog/v2` публикует `capabilities.installReview`; activity заданий — `installReview` на верхнем уровне:

```json
{"version":1,"previewPath":"install-preview","submitAction":"install-reviewed"}
```

Доверять только версии 1 и известным строкам путей/действий. Относительный путь разрешается внутри текущего `/api/catalog/v1/` или `/api/catalog/v2/`, не является внешним URL.

Перед подтверждением выполнить **read-only** `POST /api/catalog/v1/install-preview` (PS4) или `/api/catalog/v2/install-preview` (PS5). Он ничего не удаляет и не отправляет на установку. Тело содержит назначение (`ip` для PS4, `consoleId` для PS5), существующий `gameId`, одно из действий `all`, `selected`, `patches`, `dlc`, `install-preset`, `install-favorites` и соответствующий контекст: `packageIds`, `presetId` или `favoriteIds`. Это исходное действие выбора, ещё не `install-reviewed`.

Пример PS4 избранного:

```json
{"ip":"<PS4_IP>","gameId":"favorites","action":"install-favorites","favoriteIds":["CUSA03887","SLES53741"]}
```

Для одиночной PS5 игры `gameId` — точный branch из каталога, например `ps5:PPSA01325`. Не превращать CUSA игру на PS5 в ps5:PPSA по назначению: использовать её опубликованный branch. Для пресета сохранять контекст пресета, а не разрешать ID из всего каталога.

Ответ:

- `schemaVersion` (1/2), `consoleId`, `consolePlatform` — сверить назначение и ревизию текущего клиентского подключения.
- `selection.packageIds` — точный замороженный набор, от которого строится следующая команда. Не перечитывать избранное/пресет для submit.
- `packages[]`: `packageId`, `title`, `titleId`, `type`, `version`, `size`; `files`, `size` всего выбора.
- `device`: `consoleId`, `name`, `ip`, `platform`, `online`, `paired`, `firmware`, `freeBytes`, `eligible`, `reason`, `selectedBytes`, `queueBytes`, `requiredBytes`, `pending`, `queuedPackages`, `installedPackages`, `reviewToken`.
- `device.installedPackages[]`: выбранные уже присутствующие пакеты с `detail`, `canOverwrite`, `canReinstall`, `reinstallReason`, `affected`. Состав прочитан с приставки, локальные отметки приложения не являются подтверждением.

Отсутствие/неверный тип поля не заменять нулём свободного места или разрешением установки. `reviewToken` — 64 строчных hex; отсутствующий/ошибочный токен запрещает submit. При `eligible:false` показывать причину, подтверждение выключено. При изменении выбора, профиля или WEB старый preview отбрасывается, требуется новый.

### 7.2. Экран подтверждения

Показать количество и объём точного набора и назначение. Уже установленное показать отдельной таблицей/списком с галочками и действием «Переустановить все доступные». По умолчанию галочки переустановки выключены: уже присутствующее пропускается, новые выбранные пакеты устанавливаются.

Галочка разрешена только при `canOverwrite:true` или `canReinstall:true`. Для запрета вывести `reinstallReason`/`detail`. `affected` показать до подтверждения: удаление базовой игры может затронуть её патчи/DLC. Не подмешивать affected в выбранный набор и не утверждать, что они будут восстановлены, если их packageIds отсутствуют в `selection`.

`queuedPackages` показывать отдельно от установленных. Наличие в очереди не доказывает установку на PS. Все выбранные игры проверяются независимо; один присутствующий пакет не превращает весь набор в установленный. Не использовать старые локальные отметки и не добавлять чужие старые пакеты типа Little Nightmares из истории.

### 7.3. Submit через существующую квитанцию

После явного подтверждения — один POST на обычный command-маршрут:

```json
{
  "ip":"<PS4_IP>",
  "consoleId":"<ID_FROM_PREVIEW>",
  "requestId":"<NEW_32_LOWERCASE_HEX>",
  "gameId":"review",
  "action":"install-reviewed",
  "packageIds":["<EXACT_PREVIEW_PACKAGE_ID_1>","<EXACT_PREVIEW_PACKAGE_ID_2>"],
  "overwritePackageIds":["<APPROVED_INSTALLED_PACKAGE_ID_1>"],
  "reviewToken":"<64_HEX_FROM_PREVIEW_DEVICE>"
}
```

PS5 структура та же **без ip**, consoleId обязателен. PS4 consoleId тоже обязателен для нового действия и должен совпадать с профилем указанного IP. Пустой `overwritePackageIds:[]` означает пропустить уже установленное. Все overwrite ID входят в замороженный packageIds. Для нового submit максимум 10000 packageIds; старый PS4 selected-preview сохраняет существующее ограничение 128. Если клиент имеет меньшие буферы — показать ограничение до отправки, без тихого обрезания.

WEB повторно проверяет устройство, ревизии, место и исходный набор; устаревший обзор даёт failed/409 без удаления и установки. Пользователь обновляет preview и подтверждает новый выбор с **новым** requestId. Lost POST → GET первоначальной квитанции, без повторного POST и без нового ID. Не менять overwrite-массив при повторном чтении той же команды: конфликт fingerprint даёт 409.

PS4 receipt `pending → accepted|failed|uncertain`, `result` содержит `consoleId`, `name`, `state`, `message`, при запуске `queueId` (у выбранной переустановки это flow ID). PS5 receipt `pending → completed|failed|uncertain`, возвращает сообщение и доступный queueId. `accepted/completed` подтверждает команду, **не установку игры**. Если всё присутствующее пропущено, сообщение прямо говорит об этом. Дальше читать activity, а не помечать весь набор installed локально.

Замены PS5 Folder/образов/DLC не включать по аналогии с PKG: ориентироваться на фактические `canOverwrite/canReinstall` ответа. На старом WEB без installReview сохранять прежнюю обычную установку с её серверными проверками; новую выборочную переустановку не предлагать и явно требовать обновления WEB. Не направлять новую кнопку в прежний whole-game reinstall.

## 8. Проверки до передачи сборок

Осмысленные тесты в каждом клиенте:

- Старый WEB: нет taskControls/canDismiss/maintenance; новые кнопки выключены, прежние cancel/clear работают.
- Новые поля строго типизированы; PS5 opaque id отличается от packageId, команда использует правильный ID.
- PS4 failed-очередь с installed, failed и неотправленным pending: галочка pending и очистка failed доступны по ответу; installed не теряет регистрацию.
- Выбор одной записи и ветки: точные queueId, packageIds/branchId; две попытки одной игры и две приставки не смешиваются.
- Ветка более 50 строк: команда содержит branchId, не только ID текущей страницы. Более 256 выбранных строк — явное ограничение/несколько подтверждённых команд, а не тихое обрезание.
- PS4 принятое задание отменяется асинхронно и остаётся в UI до подтверждения; PS5 принятая системная установка не скрывается.
- Остановка выбранной переустановки получает maintenanceId из ответа, не ID очереди; обновление службы не получает эту кнопку.
- Потеря POST-ответа → GET старой квитанции, ровно один POST; 404, uncertain, failed и 409 не ведут к повторному удалению.
- Смена профиля, фильтра/страницы и устаревший ответ; выбор/фокус не перепрыгивают на другую игру.
- Частичный успех команд разных очередей и исчезновение последней строки страницы.
- Preview двух/трёх игр: одна отсутствует, остальные установлены; по умолчанию отправляется только отсутствующая. Отметить все разрешённые — в команду входят все отмеченные packageIds, включая SLES/SLUS, а не только первая игра.
- Удаление базы с affected: предупреждение до подтверждения, невыбранные компоненты не подмешиваются в installation selection.
- Устаревший reviewToken / changed profile / нехватка места: нет submit без проверки; failed/409 → новый preview и явное подтверждение, не повтор удаления.
