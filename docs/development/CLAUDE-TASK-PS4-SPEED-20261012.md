## Точный договор, под который уже подготовлен WEB

Все маршруты ниже — HTTP порт **12801**, текущая Bearer авторизация, текущий ключ и автоматическое сопряжение без кода. Заголовок Origin запрещён. Ключ не возвращать в публичном статусе. Текущее написание service **`PackegeFlowService`** сохранить для совместимости.

### GET /benchmark/info

Авторизованный JSON, HTTP 200, пример:

```json
{"service":"PackegeFlowService","protocol":"speed-test-v1","benchmarkApi":1,"ready":true,"busy":false,"maxBytes":268435456,"modes":["latency","upload","download","disk"]}
```

WEB проверяет все эти поля. `ready` означает, что реализация проверена на реальной PS4. До аппаратной квалификации отдавать `ready:false`; предусмотреть способ включить её после проверки, не привязывая к IP стенда. `busy` должен отражать активную установку BGFT, удаление, обновление службы или другой тест. GET должен оставаться доступным при активном тесте. Задержка измеряется WEB девятью GET: первый прогревочный, восемь входят в результат. Сравнение часов двух машин не используется.

### Потоковые маршруты

| Режим | Метод и путь | Поведение |
| --- | --- | --- |
| upload | POST /benchmark/upload | Получить синтетические данные и отбросить, без файла и без хеширования |
| download | GET /benchmark/download | Отдать синтетические данные без чтения с диска |
| disk | POST /benchmark/disk | Получить и записать временный файл, завершить fsync, сверить размер, удалить свой файл |

Каждый запрос содержит `X-PackageFlow-Size: N` и `X-PackageFlow-Request-Id: UUID`. Размер — целое от 1 МиБ до 256 МиБ включительно; WEB предлагает 64/128/256 МиБ. POST: `Content-Type: application/octet-stream`, `Content-Length: N`, тело ровно N байт (WEB генерирует 0x5a блоками по 1 МиБ). GET download: без тела. Успешный потоковый ответ **обязательно повторяет `X-PackageFlow-Request-Id`**; иначе WEB отвергает результат. WEB использует `Connection: close`, запрет редиректов, отдельный AbortSignal и предел 120 секунд.

Ответ download: HTTP 200, `Content-Type: application/octet-stream`, `Content-Length: N`, ровно N байт, генерируемых небольшим переиспользуемым буфером. Не выделять N байт целиком. HTTP chunked encoding не нужен: длина известна.

Успешный ответ upload/disk: HTTP 200, JSON до 4096 байт:

```json
{"protocol":"speed-test-v1","mode":"disk","bytes":67108864,"complete":true,"cleanup":true,"elapsedMs":850.5,"writeMs":220.0,"syncMs":3.5,"receivePipeline":true}
```

`mode` соответствует запросу, `bytes` равен N, `elapsedMs` — положительное время по монотонным часам, включая приём и завершение записи/fsync для disk. `writeMs`/`syncMs` — неотрицательные значения. `receivePipeline:true` выставлять только при фактическом перекрытии приёма и записи. Для upload: mode upload, writeMs/syncMs 0, cleanup true означает, что файл не создавался. Для disk complete/cleanup true отдавать **после** проверки полного размера, успешного fsync и удаления файла. При ошибке уборки не заявлять успех. WEB рассчитывает общую скорость дополнительно по своему времени от начала запроса до подтверждения. Это сеть + файловый ввод-вывод, а не отдельная скорость SSD/HDD и не обещание скорости установки PKG.

Ошибки: прежняя авторизация 401/403; любой Origin 403; неверный UUID/размер/длина/тип тела 400 или 413; занятая приставка/второй тест 409. Старые службы отдают 404, и WEB просит обновить службу. Не запускать тест в обход BGFT busy, не приостанавливать/отменять пользовательскую установку автоматически.

## Реализация и устойчивость

1. Сначала прочитать `main.c`, `http.c`, `install.c`, текущие ограничения HTTP и механизмы авторизации/busy. Новое потоковое тело отделить от JSON API. Не увеличивать лимит JSON до размера теста.
2. Ограниченный буфер/кольцо с приёмом и записью одновременно; разумный начальный предел памяти до 16 МиБ. Сравнить варианты блоков 1/2/4 МиБ после базового рабочего варианта. Не выделять весь тест в RAM. Проверить потоковые SDK функции, не заимствовать адреса/offset PS5.
3. Не блокировать основной цикл службы длинными recv/write/fsync: статус, отмена обычных заданий и соединения других клиентов должны отвечать во время теста. Один тест на одной PS4; независимые PS4 не блокируют друг друга.
4. Таймаут без новых данных 10 секунд, общий предел тела до 90 секунд, чтобы завершиться раньше WEB 120 секунд. Проверять короткое тело, EOF, превышение Content-Length, дубликаты/конфликтующие заголовки, частичные заголовки, abort и отключение кабеля. Успех только при полном N. Отмена WEB закрывает поток; служба должна заметить разрыв и убрать свою временную запись.
5. Временный файл в отдельном служебном каталоге, например `/data/PackegeFlowService/benchmark/`, уникальное имя по UUID. Запрет symlink/hardlink, проверка типа файла. Удалять только собственный зарегистрированный временный файл, не каталоги игр/сохранений. После перезапуска убирать только записи собственного журнала тестов. Busy освобождать после завершения уборки.
6. Сохранить прежние API установки, диагностику BGFT, подтверждение фактической установки, проверку FW, перезапуск службы, идентификаторы/квитанции, восстановление очередей, отзыв ключа. Изменения тестов не должны создавать install job.
7. Для ускорения PS4 сначала собрать времена BGFT download/install, скорости и ошибки без изменения Sony вызовов. Указать, какие реальные ограничения выявлены. Если SDK не предоставляет настройки сетевых буферов BGFT, прямо написать это. Оптимизация HTTP отдачи/Range/чтения источника на WEB — работа Codex после этих замеров.

## Что уже делает WEB Codex

Модалка «Тест скорости» в «Устройствах» имеет подписи PS4/PS5. Для PS4 четыре теста, сохранение результатов, отмена через AbortSignal. Все вызовы идут сервером WEB к 12801 с Bearer и без Origin, без fallback к PyLoader. WEB проверяет идентификатор запроса, полный объём, протокол и cleanup, не считает неполный тест успешным. Во время теста новые установки на той же PS4 блокируются; другая PS4 через service допускается. Активная установка не останавливается тестом. Старая/неквалифицированная служба показывает сообщение вместо запуска. Следующий этап — сверить твой кандидат и измерить реальную PS4.
