# PS5 speed diagnostics and durable batches — candidate 018

Implemented and exercised on PS5 Slim 13.60 with installed Windows WEB,
2026-10-12. Development candidate; no push or public release. Claude's PS4 2.06
and PS5 01.000.042 applications were not edited or rebuilt.

## User interface and measurement

Devices → Speed test opens a modal for the selected console. It offers HTTP
round-trip latency (one warm-up plus eight timed requests), WEB → PS5 network,
PS5 → WEB network, and WEB → PS5 with disk writes and grouped flushes. Test
volumes are 64, 128 and 256 MiB. Speed is byte count / monotonic elapsed time,
shown as MiB/s and decimal Mbit/s. The browser does not carry the test data.
Network tests generate bytes in memory; NAS reads and game hashing are excluded.
The disk test includes the network and receive/write path: it is **not an
isolated SSD benchmark**. Its write/flush timing helps identify overhead.

The modal pauses/resumes an existing PS5 transfer before system installation,
without cancelling its receiver data. Queue identity and confirmed offsets stay
on disk. A paused queue cannot silently be replaced, and the Tasks section can
resume it too. Cancelling all items releases a paused queue for a new queue.

Tests can be stopped. Incomplete data, a failed receipt or unconfirmed cleanup
never produces a successful speed. Reopening the modal retains the last job;
terminal results are stored outside the replaceable build in
`consoles/<consoleId>/speed-result.json`, without credentials. Tests for PS4 are
not advertised as working: its service needs a corresponding implementation.

## Protocol and resource bounds

Authenticated ELF routes:

| Route | Method | Meaning |
| --- | --- | --- |
| `/api/v1/benchmark/info` | GET | Exact `speed-test-v1` readiness receipt |
| `/api/v1/benchmark/upload` | POST | Receive generated bytes without disk |
| `/api/v1/benchmark/download` | GET | Send generated bytes without disk |
| `/api/v1/benchmark/disk` | POST | Receive/write/flush and delete own file |
| `/api/v1/transfers/batch` | POST | Durable transfer group, maximum 16 MiB |

Benchmark sizes are declared by `X-PackageFlow-Size`, bounded to 1–256 MiB,
with exact body framing. A 256 KiB ELF buffer and 1 MiB WEB generator avoid a
whole-volume allocation. Socket timeouts and a 30-second service limit bound
work. Disk tests create only a private `run-XXXXXX` file under the benchmark
root, require volume plus 32 MiB spare, and remove that file on success/error or
disconnect. Startup removes only narrowly identified private orphan files.
WEB serializes tests per console and rejects queue resume and other mutating
PS5 requests while a measurement is running.

Readiness requires the build-specific private `qualified-018` receipt and the
checked 13.60 firmware. The marker has exact contents and private ownership /
permissions; host tests check both valid and readable-by-others cases. It was
written only after hardware network, durable transfer and recovery checks.

Folder streaming negotiates `batchMax=16777216`; absent/unqualified receipts
retain the legacy maximum 4 MiB. Batches keep the existing order of data fsync,
hash checkpoint and durable state publication. ACK means durable bytes, not
bytes only in RAM. Checkpoints accept a last group up to 16 MiB; after restart
only that last group needs validation when the checkpoint is valid. Persistent
batch connections yield to waiting control clients or close after 200 ms idle.
WEB keeps two source/send buffers (at most 32 MiB for these buffers). The ELF
still receives a group before writing/hashing it: this is not a complete
concurrent receive/write worker pipeline.

## Verification and observed results

- ELF `make test` and PS5 SDK build pass, including disconnect cleanup, durable
  batch replay rejection, late seal and bounded checkpoint recovery.
- Nine relevant WEB test files and Nuxt production build pass. Folder test
  covers a lost 16 MiB ACK without retransmitting that group.
- Hardware: exact 128 MiB upload/download, bounded size/authentication refusal;
  two 64 MiB durable fixtures, final BLAKE3 proof and mismatched replay refusal.
- Hardware restart: after 16 of 32 MiB, ELF restart retained the exact durable
  offset; remaining bytes resumed and final BLAKE3 verification succeeded.
- Playwright against the installed Windows WEB: modal rendering, all four
  tests, result rows, reopening, no page exceptions. Concurrent start and queue
  resume return 409 during a test. Cancellation completes; FTP confirms no
  benchmark temporary file remains. Only journaled synthetic fixtures removed.

| Measurement | Observed MiB/s |
| --- | ---: |
| Direct Windows → PS5 synthetic network (Node harness) | 110.0 |
| Direct PS5 → Windows synthetic network (Node harness) | 111.5 |
| Network plus receive/write/flush path | 45.3 |
| Durable 4 MiB groups, 64 MiB identical fixture | 44.9 |
| Durable 16 MiB groups, 64 MiB identical fixture | 58.8 |
| Installed WEB network upload / download | 107.4 / 99.5 |
| Real NAS → Windows WEB → PS5 Avatar, before / after | 31.6 / 42.0 |

Installed WEB HTTP latency median 5.0 ms (4.3–12.6 ms in eight requests).
Fixture improvement about 31%; real 20-second Avatar sample about 33%.
These are short samples, not guaranteed whole-install averages. Network capacity
is near gigabit; receive/write/hash processing and per-file work still reduce
actual installation throughput. No final Avatar installation is claimed.

Queue and both user-selected transfers were retained. Avatar resumed from
102,060,457,021 confirmed bytes without creating another queue or dispatching a
second installation. The ASTRO package remains behind it. The installed master
and WEB bootstrap bundle both received ELF 018, keeping Claude's app artifacts.
