# PS4 2.09: аппаратные A/B-замеры потоков службы

12 октября 2026. PS4 Pro 10.1.10.32, FW 12.50; компьютер с WEB/исходниками 10.1.10.47. Пользователь сам установил 2.09. Проверено через Bearer API службы **12801**, PyLoader не участвовал. Нативные исходники Codex не менял. Пакеты игр не устанавливались и не удалялись, пользовательская отменённая очередь Mulaka сохранена.

## Результат

Увеличенный сокетный буфер воспроизводимо ускорил синтетическую сеть с примерно 41 до 110 МиБ/с. Запросы на 1 и 2 МиБ фактически дают **512 КиБ**; SDK set/getError=0. Обычный режим службы не изменён: профили применяются только во время своего теста. Реальная установка PKG через BGFT не измерялась, поэтому ей этот прирост не приписывается.

Исходники Claude: d00452e + af2cd91, кандидат BENCHMARK_READY=1, NET_POOL_KB=256. Локальный PKG 6619136 байт, SHA256 `4e8474dcc555513b14dd65243e2f6394bd9dc843523691bfa0ea7e477c0ed87b`. На приставке проверены pkgVersion=2.09 и diagnosticsVersion=1; хеш установленного бинарника не извлекался.

## Метод и сеть

Каждый поток 256 МиБ искусственных данных, один тест на приставку. POST передаёт Content-Length, GET проверяет точный размер, запрос UUID/эхо, авторизация без Origin. Upload/disk проверяют complete/cleanup и JSON <4096 байт. Download диагностика считывается из lastTest после busy=false. Скорость считается компьютером от начала запроса до полного ответа; сохранение/уборка входят в disk. Память источника — переиспользуемый 1 МиБ блок, целый объём не выделяется.

Для сети по три повтора каждого профиля; во втором круге порядок профилей обращён после baseline. В таблице медиана и min–max, **МиБ/с**, не Мбит/с.

| Профиль | WEB → PS4 | PS4 → WEB |
| --- | --- | --- |
| baseline | 41.62 (41.49–41.73) | 40.75 (40.34–40.81) |
| sleep500 | 89.25 (87.23–89.60) | 67.24 (63.65–70.05) |
| polls16 | 41.60 (41.59–41.70) | 40.59 (39.99–41.00) |
| sockbuf256k | 82.77 (82.49–82.95) | 74.33 (74.22–78.50) |
| sockbuf1m | 110.04 (108.43–110.86) | 105.11 (104.38–107.86) |
| sockbuf2m | 110.73 (110.61–110.76) | 109.47 (93.55–110.25) |

`sockbuf2m` приём 110,73 МиБ/с ≈929 Мбит/с, медиана отдачи 109,47 МиБ/с ≈918 Мбит/с. Это полезная скорость потоков, не чтение скорости физического линка. NetCtl deviceRaw=0, linkRaw=1, MTU=1500, speedMbps=null.

База: RCVBUF 66608 (в одном тесте исходный 82992), SNDBUF 33304 байт. sockbuf256k — 262144; sockbuf1m/sockbuf2m — 524288. Измеренный сон базы примерно 2,6–2,8 мс при запросе 2 мс, sleep500 примерно 0,9 мс при запросе 500 мкс. polls16 практически не помог; увеличение буфера помогло при прежнем сне. Запрос 512 КиБ ещё не измерен: нужен отдельный кандидат/профиль.

Финальная база после отката профилей: приём 41,60, отдача 39,81 МиБ/с, прежние сокетные буферы. Это подтверждает, что ускоренная настройка не осталась включённой постоянно.

## Запись: результат неоднороден

Успешные завершённые disk-тесты ниже перечислены **в порядке повторов**, без объявления причинного выигрыша профилей.

| Профиль | Завершённых повторов | МиБ/с по повторам |
| --- | --- | --- |
| baseline | 3 | 41.54, 40.97, 4.43 |
| sleep500 | 3 | 72.27, 38.80, 10.02 |
| polls16 | 2 | 41.56, 32.48 |
| sockbuf256k | 2 | 73.94, 60.84 |
| sockbuf1m | 2 | 88.30, 61.50 |
| sockbuf2m | 2 | 92.52, 46.73 |
| ring2m | 2 | 41.35, 4.91 |
| ring4m | 2 | 41.20, 4.83 |

На первом круге sockbuf1m/2m с записью дали 88,30/92,52 МиБ/с. Затем скорость записи упала: ring2m/4m около 5 МиБ/с, а следующий неизменённый baseline — **4,43 МиБ/с**, writeMs=55540,205. Сеть при этом сохранила результаты. Поэтому нельзя считать низкие последние значения доказательством плохого размера кольца или чистым A/B. Причина накопленной/фоновой нагрузки, файлового ввода-вывода либо другого фактора пока неизвестна. ringFull и время write выросли; fsync существенно меньше времени write.

После третьего disk baseline и sleep500 Codex остановил **только свой** следующий disk polls16, закрыв клиентское соединение; оставшиеся повторы сети завершил отдельно. Дальнейшие полные disk-повторы и финальную запись не выполнял. Это изменение метода сохранено в JSON. Всего **56 полных успешных потоков**: 38 сетевых (36 сравнительных + 2 финальные базовые) и 18 с записью, плюс проверки отмены. Кольцо по умолчанию остаётся 8 × 1 МиБ.

## Занятость, отмена, уборка

Во время собственного удерживаемого disk-запроса info ответил за **3,62 мс**, busy=true. Авторизованные POST с пустыми телами на /install/jobs, /install/local, /files/mkdir, /apps/remove получили **409 speed_test_active** до обработки этих тел; пользовательских мутаций не было. Реальные PUT, локальный UI и другие маршруты отдельно на приставке не проверялись (host-проверки Claude указаны в его отчёте).

После abort busy=false, запрос отменён, /data/PackegeFlowService/benchmark пуст (entries=0). В конце ready=true и busy=false.

В первой серии между успешными тестами получен один 409. Скрипт остановился; активного задания установки после проверки не было, info busy=false. Тело того ответа не сохранено, причина не установлена. Продолжение сохраняет отдельные отказы и допускает ограниченный повтор только после проверки свободной консоли; дополнительных 409 не получено. Не выдавать эту проверку за диагностику всех причин занятости.
