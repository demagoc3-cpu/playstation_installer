# Claude: следующий этап — скорость потоков службы PS4

12 октября 2026. Пользователь передаёт задание самостоятельно. Нативную службу PS4 исправляет Claude, WEB — Codex. Не делать push, не отправлять кандидаты на приставку самостоятельно. Не менять SDK вызовы BGFT без подтверждённой документации.

## Проверенная база

`67093cf` проверен Codex на PS4 FW 12.00, IP 192.168.0.113 через Windows WEB. PS4 подключена **кабелем** (ответ пользователя), не Wi-Fi. Замеры шли через нашу службу 12801, PyLoader не участвовал.

Кандидат 2.07: SHA256 `c14e6468cf7819acde8475dd6c5cc69524f8cbb38c36f9464ea2ff244a98ce3f`, ready false. Все четыре режима 64 МиБ и потоки 256 МиБ прошли. Диск приём/запись параллельно, cleanup true. Отмена 256 МиБ прерывает поток, busy снимается, каталог benchmark пуст. info отвечает во время потока за 3,6 мс. Host-тесты настоящего PS4-объекта benchmark и install прошли вне sandbox (внутри sandbox локальный AF_UNIX send возвращал EPERM; это ограничение окружения, а не сбой службы).

| Тест | 64 МиБ | 256 МиБ |
| --- | --- | --- |
| WEB → PS4 сеть | 33,3 МиБ/с | 40,3 МиБ/с |
| PS4 → WEB сеть | 41,2 МиБ/с | 41,8 МиБ/с |
| WEB → PS4 сеть + запись | 32,8 МиБ/с | 40,5 МиБ/с |

Для 256 МиБ disk writeMs 1163,851, syncMs 17,525, общая передача 6327,172 мс. Сеть без записи уже существенно ниже ожидаемого гигабитного потока; диск в этом тесте почти не снижает общий результат. Это **не** доказательство ограничения физического линка: возможны сон цикла, размеры сокетов, Sony net pool, обработка HTTP, Windows источник. Скорость реальной установки через BGFT — отдельный путь, её должен замерить Codex через `timing`.

Codex упаковывает тот же код с BENCHMARK_READY=1 и номером 2.08 только в копии сборки; корневые исходники твоего проекта не менял. WEB 75e765a умеет модалку PS4. Не откатывай автоматическое сопряжение, изоляцию очередей и ready.

## Дополнительная проверенная приставка

Пользователь подготовил вторую PS4 Pro 10.1.10.32, FW 12.50, обновил её до 2.08. Codex измерил через WEB компьютера с исходниками 10.1.10.47: на 256 МиБ приём 41,4 МиБ/с, отдача 40,0 МиБ/с, сеть + запись 41,2 МиБ/с, задержка 17,0 мс. Pipeline/cleanup true, все четыре результата сохранены и отображены в модалке. Первая приставка на другом компьютере даёт сходный результат; это усиливает гипотезу общего ограничения потока службы, но не доказывает размер буфера или сеть как причину. В idle код спит 16 мс, во время теста 2 мс: измерять фактическую длительность сна, а не только запрошенную. Не менять нативные исходники ради тестов второй PS4 без отдельного кандидата. Её пользовательские очереди/игры не удалять.

## Задача

1. **Сначала измеряемые параметры.** В диагностике benchmark добавить версионированные поля фактического SO_RCVBUF/SO_SNDBUF, ошибок чтения/установки опций, числа recv/send/poll и EWOULDBLOCK, байт на вызов и фактического времени ожидания/сна. Отдельно показать настройки и реальный интерфейс из доступного SDK NetCtl, если они читаются. Не выдавать кабель за доказательство согласованного 1 Гбит/с: если SDK не отдаёт скорость линка, показывать неизвестно. JSON upload/disk держать <4096 байт, обязательные поля/эхо Request ID сохранить.
2. В `main.c` сейчас `sceNetPoolCreate(...,256*1024,0)`, benchmark сон 2 мс, до 4 poll за итерацию; сокеты получают nonblock, но размеры send/recv явно не задаются. Это **кандидаты для проверки**, не доказанные причины. Через реальные SDK константы и `sceNetGetsockopt` проверить доступность опций. Не выдумывать значения констант. Настройки инициализации сети проверять до запуска, ошибки не игнорировать. Не смешивать net pool службы и 1 МиБ управляющей кучи BGFT: это разные ресурсы.
3. Подготовить сравнимые экспериментальные профили с фиксированным пределом памяти: текущая база; сон 2 мс/500 мкс или ожидание готовности сокета по проверенному SDK; подходящие socket buffers, если поддерживаются; размер net pool, если он действительно влияет и подтверждены требования SDK. Менять по одному параметру. Сохранять обычный сон/нагрузку CPU вне теста. Не делать бесконечный busy-spin. Следить за latency/status других клиентов и SDK ошибками.
4. Проверить буферы кольца disk 1/2/4 МиБ, но **не ожидать ускорения сети от увеличения кольца**, пока сеть без диска медленная. Ограничение ring ≤16 МиБ, не выделять весь N. Обязательно сохранять fsync и cleanup.
5. Не добавлять многопоточную установку пакетов на одной PS4. Несколько приставок работают параллельно только через отдельные сервисные очереди. PyLoader остаётся одноконсольным. Прежние API установки/удаления/отмены/перезапуска, FW проверки, ключ и журнал не менять.
6. Закрыть обратное направление busy на стороне службы: сейчас benchmark не начинается при BGFT/files/apps/update, но обычные обработчики после старта benchmark не проверяют `pfs_benchmark_active()`. WEB блокирует собственные submit, но нативный UI/другой WEB обходят его. Добавить admission 409 для новых конфликтующих мутаций, включая локальные маршруты и PUT upload; оставить чтение status/info и отмену прежних задач доступными. Проверять до Sony/файловой мутации, не блокировать только post factum.
7. Тестировать actual PS4 objects, HTTP parsing/auth/Origin, подстановку ошибок socket options, rollback профиля, bounded memory, short/extra/abort/full disk, отзыв busy после уборки, latency под нагрузкой. Прежние test-ps4-benchmark/install/smoke/UI проходят.

## Результат

Локальные коммиты и `CLAUDE-REPORT-PS4-THROUGHPUT-20261012.md`: поддерживаемые SDK опции/константы и источники, экспериментальные профили, как выбрать каждый без вшитого IP, способы отката, тесты, кандидаты и SHA256. Если Sony net API имеет реальное ограничение, обосновать измерениями; иной транспорт только отдельным кандидатом с сохранением авторизации, busy и уборки. Ни число потоков, ни увеличенный буфер сами по себе не гарантируют гигабит.

Аппаратные A/B замеры делает Codex на Windows и PS4. Настройки готового профиля выбираем после повторяемых результатов на 256 МиБ и проверок разрыва. На сейчас не заявлять ускорение BGFT или всех пакетов по результатам синтетического benchmark.
