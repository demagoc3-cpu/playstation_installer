# Claude: следующий этап после аппаратного A/B 2.12

Codex проверил кандидат 2.12 на PS4 Pro FW 12.50. Отчёт: `CODEX-REPORT-PS4-212-STARTUP-FILE-AB-20261012.md`; данные: `evidence/ps4-212-startup-file-ab-20261012.json`. WEB и самостоятельный ELF PS5 остаются за Codex. В этой задаче меняется только служба PS4: кандидат и host-тесты, без передачи на приставки и push. Код STORM не переносить: пользователь разрешил только изучение.

## Аппаратные результаты

1. Реальный Far Cry, int/service: первые байты через 32543/32602 мс, первый запрос манифеста через 30092/30115 мс после dispatch, подготовка WEB 8 мс. Оба вызова Start заняли 2 мс. На этом пакете service не помогает; сохранить int по умолчанию. Это одна попытка на режим, а не доказательство невозможности ускорения всеми способами. Новые опции Sony без первичного основания не добавлять.
2. Последовательность baseline/short/short/baseline: короткий info 16.7/2.9/2.1/16.8 мс; чтение 256 КиБ 14.4/21.3/22.9/14.4 МиБ/с; чтение 4 МиБ 43.5/43.0/46.9/44.5 МиБ/с. PUT с finish 47.3/63.1/59.0/36.9 МиБ/с. Все SHA256 совпали, cleanup=true, настройки возвращены baseline/int.
3. PUT 32 МиБ, short/1: клиент 503 мс, write 155 мс, fsync 31 мс; short/2: клиент 538 мс, write 68 мс, fsync 160 мс. Бывают выбросы write до 85–92 мс. Отдельный писатель имеет смысл как ограниченный эксперимент; не объявлять его полным решением и не обещать гигабит.
4. Native отдача 32 МиБ блоками 4 МиБ занимает 499–574 мс. EWOULDBLOCK: 171–291 на восемь запросов, handle около 6 мс. headersUs после accept не измеряет очередь до accept. Не объяснять ограничение крупных чтений одним idle 16 мс: short не улучшил их устойчиво.

## Задание

- Подготовить short по умолчанию отдельным кандидатом после host-регрессий: открытый клиент или недавняя активность включают 1 мс, настоящий простой оставляет 16 мс, без busy-spin. Сохранить явный baseline для отката. Не увеличивать частоту опроса BGFT, лимиты JSON и бюджет чтения.
- Добавить один явно включаемый профиль асинхронного PUT-писателя с фиксированной памятью и кольцом, принимающего данные параллельно write/fsync. Ответ с новым offset разрешён только после durable commit. Сохранить exact offset, повтор прежнего блока, revision, cancel, abort, ошибки fsync и отзыв ключа. Не выдавать успешное подтверждение при неподтверждённой записи. По умолчанию оставить прежний писатель. Сохранить busy и отклонение benchmark до изменения данных.
- Если писателю нужно изменение API, сначала описать договор и причину. Не ломать клиентский PUT 4 МиБ и восстановление. Нельзя держать весь upload в памяти или создавать вторую копию игры.
- Для крупного чтения сначала отделить ожидание готовности send, число порций и фактический сон от чтения диска. Проверить взаимодействие двух клиентов. Если лишний сон подтвердится, предложить ограниченный профиль drain без busy-spin. Сохранить бюджет чтений 8 МиБ, максимум запроса 4 МиБ и ответ 503 с освобождением памяти.
- Host-тесты на настоящих объектах и HTTP: медленный приёмник и писатель, status/cancel параллельно, два чтения по 4 МиБ и третий 503, разрыв/ошибка fsync/abort без утечки, совпадение SHA256. Не менять вызовы Sony по умолчанию. Собрать кандидат с BENCHMARK_READY=1, сообщить коммит, размер и SHA256.

Аппаратный тест и принятие кандидата выполняет Codex. Скорость собственных файловых сокетов не объявлять скоростью BGFT: он использует своё соединение Sony.
